  - Bug it catches: Setup precondition broken — the rest of the test is meaningless if the first register failed.

  - Bug it catches: Controller returns 2xx and creates a second row (no unique constraint, or constraint not enforced because Hibernate validation is off), or returns 5xx because the integrity violation was not caught.

3) POST loginPath() with the wrong-password body.
4) Read the status code and assert strictly 401, with explicit guards against 2xx, 5xx, 404, and 403.	• Register status 200..299 (precondition)
  - Bug it catches: Setup failure — invalidates the rest of the test.
• Login status strictly 401
  - Bug it catches: Anything other than 401 is a misclassification of authentication failure.
• NOT 2xx
  - Bug it catches: Login skipped the password check and minted a token anyway — critical security bug (anyone with any password can impersonate any user).
• NOT 5xx
  - Bug it catches: Bcrypt mismatch threw an unhandled exception (e.g., IllegalArgumentException from a malformed hash) that leaked instead of being caught and translated to 401.
• NOT 404
  - Bug it catches: OWASP user-enumeration leak — returning 404 vs 401 distinguishes "user exists but wrong password" from "no such user", letting attackers enumerate valid emails.
• NOT 403
  - Bug it catches: Controller treats login as a permissioned action (mapping any auth failure to 403 generically) instead of distinguishing "not authenticated" (401) from "authenticated but lacking permission" (403).

8	TC08 — Tampered JWT signature is rejected with 401 (negative path)	public, authentication	adminToken() (setup), GET crudCollectionPath(firstTopLevelNonUserEntity()) with tampered Bearer token	The auth filter must perform real cryptographic verification of the JWT signature, not merely decode the structure. The catastrophic security bug it targets is when a student extracts claims (uid, role) directly from the base64-decoded payload without validating that the signature matches: an attacker can then forge any token by editing the payload and re-base64'ing, with the original or any signature, and gain unauthorized access. 2) tamperSignature(token) — keep the original header and payload intact, but replace the third (signature) segment with the base64-url of "tampered-signature-does-not-verify". The result still parses as a JWT (3 dot-separated segments, valid base64) but the signature is mathematically wrong.
3) Resolve firstTopLevelNonUserEntity() and compute crudCollectionPath("Account") (same endpoint family as TC06/TC07).
4) GET that path with Authorization: Bearer <tampered-token>.
5) Assert strictly 401.	• GET status strictly 401
  - Bug it catches: Filter is not verifying signatures correctly. Anything else means the signature check is broken or absent.
• NOT 2xx
  - Bug it catches: Critical security bug — the signature is not being verified. Code like Jwts.parser().setSigningKey(key).parseClaimsJws(token).getBody() may have been replaced with Jwts.parser().parseClaimsJwt(token) (no signature check) or claims read directly from the base64 payload. Anyone can forge tokens.
• NOT 5xx
  - Bug it catches: SignatureException/MalformedJwtException is leaking unhandled instead of being caught and translated to 401.
• NOT 404
  - Bug it catches: Filter passed the request through to the controller — signature mismatch must be caught FIRST in the security chain, not deferred to a 404 from the data layer.
• NOT 403
  - Bug it catches: Forged credentials are "not authenticated" → 401, not "authenticated but lacking permission" → 403. Returning 403 here means the student is mis-classifying signature failures as permission errors.
