## What M3 Adds to Your Codebase

**M1 built** 5 services sharing one PostgreSQL database.

**M2 added** 6 databases (polyglot persistence), authentication, caching, and design patterns — still one PostgreSQL, still cross-service SQL JOINs inside that PostgreSQL.

**M3 finishes the transformation:**

- **Database isolation** — each service gets its own PostgreSQL instance. No service can open a JDBC connection to another service's database.
- **OpenFeign** — synchronous HTTP calls replace cross-service SQL JOINs for read dependencies.
- **RabbitMQ** — asynchronous events replace cross-service write side-effects.
- **Spring Cloud Gateway** — a 6th Maven module acts as the single entry point. JWT validation moves here.
- **Kubernetes** — all services and databases deploy to a local MiniKube cluster.

### What Does NOT Change

- All 45 M1 features — except the cross-service SQL inside 17 of them (see sections below)
- All 7 M2 design patterns
- All 6 M2 databases (PostgreSQL + MongoDB + Redis + Elasticsearch + Neo4j + Cassandra)
- JWT authentication (shared secret, stays the same)
- Redis caching (all cached endpoints remain cached)
- MongoDB event logging (Observer pattern stays in place)

## New Transaction Status Values

M3 adds saga-related statuses to the Transaction entity's status enum. Finance Tracker's saga is finance-specific (transaction completion → reporting snapshot), not a payment saga, so the names differ slightly from the generic M3 template — report replaces payment to reflect that S5 is the reporting-service, not a checkout/payment service.

| New status | When it is set |
|-----------|----------------|
| COMPLETING | S3 sets this immediately before publishing transaction.completed |
| REPORT_PENDING | S3 sets this when report.initiated event is consumed (S5 has begun creating the snapshot) |
| REPORTED | S3 sets this when report.completed event is consumed (snapshot persisted to S5's PG + audit trail) |
| REPORT_FAILED | S3 sets this when report.failed event is consumed (snapshot creation failed; triggers compensation) |
| REVERTED | S3 sets this when report.reverted event is consumed (compensation cascade complete) |

The pre-existing M1 statuses (PENDING, APPROVED, COMPLETED, VOIDED) remain. COMPLETED is still set, but only after the saga reaches REPORTED — i.e., the audit trail proves the transaction is fully settled.

## Section 1 — Database Isolation

### 1.1 What Changes

Every service previously connected to a single shared database:

```yaml
spring:
  datasource:
    url: jdbc:postgresql://postgres:5432/financedb
```

In M3, each service connects to its own database on its own PostgreSQL instance:

```yaml
# user-service application.yml
spring:
  datasource:
    url: jdbc:postgresql://user-postgres:5432/financedb-users

# account-service application.yml
spring:
  datasource:
    url: jdbc:postgresql://account-postgres:5432/financedb-accounts

# transaction-service application.yml
spring:
  datasource:
    url: jdbc:postgresql://transaction-postgres:5432/financedb-transactions

# budget-service application.yml
spring:
  datasource:
    url: jdbc:postgresql://budget-postgres:5432/financedb-budgets

# reporting-service application.yml
spring:
  datasource:
    url: jdbc:postgresql://reporting-postgres:5432/financedb-reporting
```

### 1.2 Cross-Service FK Columns Become Plain Longs

Every `@ManyToOne` or `@JoinColumn` that pointed to another service's entity becomes a plain Long field. The column still exists in the database, but there is no JPA foreign-key relationship across databases.

| Table | Column | Before (M1/M2) | After (M3) |
|-------|--------|----------------|-----------|
| accounts | user_id | @ManyToOne User user | private Long userId; |
| transactions | user_id | @ManyToOne User user | private Long userId; |
| transactions | account_id | @ManyToOne Account account | private Long accountId; |
| transactions | to_account_id | @ManyToOne Account toAccount | private Long toAccountId; |
| transactions | approver_id | @ManyToOne User approver | private Long approverId; |
| budgets | user_id | @ManyToOne User user | private Long userId; |
| saved_reports | user_id | @ManyToOne User user | private Long userId; |

Intra-service relationships stay intact: User ↔ FinancialGoal, Account ↔ AccountStatement, Transaction ↔ TransactionSplit, and the SavedReport ↔ ReportTemplate join entity (ReportTemplateUsage) remain JPA-managed because both sides live in the same service's database.

### 1.3 NoSQL Databases — Shared Instance, Separate Ownership

MongoDB, Redis, Elasticsearch, Neo4j, and Cassandra remain as single shared instances (one StatefulSet each in Kubernetes). Each service already owns its own collections/indexes/keyspace and never reads another service's data — the logical isolation from M2 is sufficient. Running 5 MongoDB + 5 Redis + 5 Elasticsearch + 5 Neo4j + 5 Cassandra StatefulSets would make MiniKube unrunnable.

**The M3 rule:** No service connects to another service's PostgreSQL. Each service continues to own its MongoDB collections (auth_events, account_events, transaction_events, budget_events, report_audit_trail), Redis key prefix, Elasticsearch accounts index (S2-only), Neo4j label set (UserNode, CategoryNode, SPENT_ON — S3-only), and Cassandra budget_usage_events keyspace (S4-only).

#### Eventual-consistency windows

Reads from NoSQL stores after a write should not assume immediate visibility:

- **Elasticsearch** has a default refresh-interval of ~1s — Account writes via M2 CRUD or S2-F11 may not be visible to S2-F10 full-text search for up to 1s after the PG commit. Tests that depend on read-after-write should add a small delay or call ES _refresh explicitly.
- **MongoDB** is acknowledged on w=1 by default — within a single MongoDB primary, writes are immediately readable, but readers using replicas with read-preference secondary may lag.
- **Cassandra** uses LOCAL_QUORUM for the keyspace (M2 default) — writes propagate within ms but are not strictly linearizable.
- **Neo4j + Redis** are immediately consistent for the saga's purposes.

### 1.4 Deliverables for DB Isolation

- user-service/application.yml — datasource URL points to user-postgres:5432/financedb-users
- account-service/application.yml — datasource URL points to account-postgres:5432/financedb-accounts
- transaction-service/application.yml — datasource URL points to transaction-postgres:5432/financedb-transactions
- budget-service/application.yml — datasource URL points to budget-postgres:5432/financedb-budgets
- reporting-service/application.yml — datasource URL points to reporting-postgres:5432/financedb-reporting
- All cross-service @ManyToOne fields replaced with Long in the relevant entities
- New saga statuses added to Transaction status enum (COMPLETING, REPORT_PENDING, REPORTED, REPORT_FAILED, REVERTED)

### 1.5 User Deactivation Policy Across Services

When User.status transitions to DEACTIVATED via S1-F4, the cross-service propagation is deliberately limited — only user-service (local) and transaction-service (via user.deactivated consumer) react. Specifically:

- **S2 account-service:** Accounts owned by a deactivated user are NOT auto-frozen. Operators may manually freeze them via S2-F4 if business policy requires it. Existing balance + statement records remain queryable.

- **S3 transaction-service:** Consumes user.deactivated and atomic-UPDATEs all the user's PENDING transactions to status=VOIDED (replaces M1 S1-F4's direct cross-service SQL UPDATE). APPROVED / saga-managed / COMPLETED transactions are NOT touched — they represent committed financial operations that remain part of the user's audit trail.

- **S4 budget-service:** Budgets owned by a deactivated user remain in their current state (ACTIVE budgets continue to exist). Auto-COMPLETING them on user deactivation would lose the audit trail of what budget the user had at deactivation time.

- **S5 reporting-service:** SavedReports + ReportTemplateUsages remain queryable for audit purposes.

**Rationale:** financial records have audit-retention requirements; auto-deletion or auto-archival on user deactivation would be a compliance violation. M3's S1-F4 active-budget pre-check enforces "cannot deactivate while ACTIVE budgets exist" so the policy of "deactivated user has no ACTIVE budgets" is approximately maintained at deactivation time, but the M3 spec deliberately accepts the TOCTOU race against concurrent S4-F4 batch budget creation (best-effort pre-check, not strict transactional consistency).

**Operator note:** if a user requests data deletion under regulations (e.g., GDPR), the operator is expected to perform a manual, cross-service cleanup using each service's CRUD DELETE endpoints — the spec does not auto-cascade.

### 2.3 Correlation ID Propagation

Every service must forward X-Correlation-ID on all outgoing Feign calls:


### 2.4 Error Handling

Wrap every Feign call in try-catch. Never let a downstream failure crash the calling service, for example:

```java
try {
    UserTransactionSummaryDTO summary = transactionServiceClient.getUserTransactionSummary(userId);
    return buildDTO(user, summary);
} catch (FeignException.NotFound e) {
    return buildDTO(user, UserTransactionSummaryDTO.empty());
} catch (FeignException e) {
    log.warn("transaction-service unavailable for user {}: {}", userId, e.getMessage());
    throw new ServiceUnavailableException("Transaction service temporarily unavailable");
}
```

### 2.5 RabbitMQ Dependency

Add to every service that publishes or consumes events:

```xml
<dependency>
    <groupId>org.springframework.boot</groupId>
    <artifactId>spring-boot-starter-amqp</artifactId>
</dependency>
```

### 2.6 RabbitMQ Connection Configuration

Add to every service's application.yml:

```yaml
spring:
  rabbitmq:
    host: rabbitmq
    port: 5672
    username: guest
    password: guest
    listener:
      simple:
        acknowledge-mode: auto
        default-requeue-rejected: false
        retry:
          enabled: true
          initial-interval: 1000
          max-attempts: 3
```

Retry interaction with idempotency: with max-attempts: 3 + at-least-once delivery semantics (§2.10), every consumer mutation must be idempotent (Critical Rule §16.12). A non-idempotent consumer that fails between commit and ACK will apply the mutation 2× on retry — the rejected-after-retry message also redelivers once before falling to DLQ. This is why every per-service consumer description in §3–§7 + §8 cites either an atomic state-conditional UPDATE (no-op on duplicate) or an explicit processed_events deduplication table.

### 2.7 Topology — What Each Service Must Declare

Each service declares its own RabbitMQ topology as Spring @Beans in a @Configuration class. The responsibilities are split:

- **Producer service** declares only the TopicExchange it publishes to.
- **Consumer service** declares the Queue, the DLQ, another TopicExchange reference (same name — Spring deduplicates), and the Binding that connects them.

Every consumer queue must have a dead-letter queue. The DLQ is wired by declaring the consumer queue with the x-dead-letter-exchange and x-dead-letter-routing-key arguments pointing at a separate dead-letter exchange + DLQ. Combined with default-requeue-rejected: false (§2.6), this means: when a listener method throws and Spring's retry exhausts (max-attempts: 3), the message is automatically routed to the DLQ — no manual basicAck/basicNack code in the consumer.

The exchange type for all Finance Tracker events is TopicExchange. This allows routing key wildcards so future events can be added without declaring a new exchange.

### 2.8 Event Payload Records

Event payloads are plain Java record classes, serialized to JSON by Jackson. They live in an events package inside the shared contracts/ Maven module:

```java
// reporting-service publishes
```

**Note on the report.events exchange:** in the M3-STRUCTURE template the S5 exchange is named payment.events because most themes have a payment service as S5. Finance Tracker's S5 is the reporting-service — it has no payment domain — so the exchange is renamed report.events and the routing keys carry report.* prefixes. The choreography topology (success / failure / refund-equivalent fan-out) is identical to Talabat; only the names reflect the theme.

**Note on observability-only events:** account.rated and account.stats-updated are consumed by reporting-service ONLY for audit-trail enrichment in report_audit_trail MongoDB. They are NOT part of the saga's forward path or compensation cascade — disabling them would not break the saga. The choice to publish + consume these events is a deliberate observability-stream design (M2-style audit telemetry) rather than a saga requirement.

### 2.10 Delivery Semantics

RabbitMQ in this M3 deployment provides per-queue FIFO ordering and at-least-once delivery. Three consequences students must design against:

1. **Duplicate consumption is possible.** A consumer that throws or whose container restarts between processing and ACK will receive the same message again. Critical Rule §16.12 mandates that every consumer be idempotent — see the atomic-UPDATE patterns in §3-§7 + §8 consumer descriptions.

2. **Cross-queue ordering is NOT guaranteed.** Within one queue, RabbitMQ delivers messages in publish-order. Across queues (e.g., S3's transaction.completed queue vs S5's report.initiated queue), no ordering is enforced — report.completed could arrive at S3 before report.initiated if the broker reorders sessions or two S5 publishes happen in quick succession. Consumers must handle out-of-order arrival via state guards: e.g., S3's report.completed consumer ignores the event if the Transaction's status is not REPORT_PENDING (e.g., already REPORTED from a prior delivery, or still COMPLETING because report.initiated hasn't arrived yet).

3. **DLQ is the terminal sink, not a re-processor.** After max-attempts: 3 retries, the message goes to the queue's x-dead-letter-exchange. Operators inspect DLQ contents manually; there is no automatic re-feed. A consumer that consistently fails (e.g., bug in deserialization) will park its messages in the DLQ — saga progress for that specific message stops until the DLQ is drained. Document this in any feature whose Behavior depends on saga progress.

## Section 3 — User Service Refactoring (S1)

### New Endpoints S1 Must Expose

user-service exposes the following endpoints for downstream services to Feign-call. The first two are pre-existing M1 endpoints (carry-over); the third is M3-new for fan-out optimization:

- **GET /api/users/{id}** (M1 CRUD) — returns {id, name, email, role, status, preferences}. Called by S2 (S2-F8 ADMIN check), S3 (S3-F2 ADMIN check, S3-F11 user details, S3-F12 user existence), S4 (S4-F3 / S4-F9 user-name lookup, S4-F4 / S4-F8 / S4-F10 existence), S5 (S5-F3 / S5-F4 existence, S5-F10 user existence + saga snapshot trigger).

- **GET /api/users/{id}/profile** (M1 S1-F8) — returns UserProfileDTO including the user's financialGoals collection. Called by S5 (S5-F10 health-score goalProgressRate computation).

- **GET /api/users/by-ids?ids={id1},{id2},…** (M3-new — fan-out optimization) — returns List<UserDTO> for batch lookup. Used by S4-F3 / S4-F9 to resolve userName for many distinct userIds in a single Feign call instead of N per-id calls. Empty list if no IDs match. Limit max 100 IDs per call (414 if exceeded).

**Auth carry-over from M2:** every endpoint refactored in §3-§7 retains its M2 auth posture — generally Required (USER) per CC-1, with the gateway JWT filter (§9.3) validating every incoming request before routing. Per-feature ownership checks (e.g., S5-F10's "JWT uid equals path userId OR role=ADMIN", S2-F12's account-owner check) are inherited from M2 and not restated per-feature in the M3 prose; refer back to the M2 spec for the exact ownership rule when implementing.

### Features That Require Feign Calls

#### [S1-F3] Get User Transaction Summary

**Branch:** feat/M3/user/S1-F3/<studentID>  
**Endpoint:** GET /api/users/{id}/transaction-summary

**M1 implementation:** Direct native SQL JOIN on the shared transactions table aggregating by user_id.

**M3 change:** Replace the SQL JOIN with a Feign call to transaction-service, so that the interface would be:

```java
@FeignClient(name = "transaction-service", url = "${feign.transaction-service.url}")
public interface TransactionServiceClient {
    @GetMapping("/api/transactions/user/{userId}/summary")
    UserTransactionSummaryDTO getUserTransactionSummary(@PathVariable Long userId);
}
```

UserTransactionSummaryDTO returned by transaction-service: {totalTransactions, completedTransactions, voidedTransactions, totalIncome, totalExpenses}

user-service calls this and merges it with the local User (for userId, name) to build the final response DTO.

**Test scenario:**

- **(setup)** In user-postgres: create User ID=1 (Ahmed Hassan, role=PERSONAL). In transaction-postgres: 5 transactions for userId=1 — 3 COMPLETED (2 INCOME amount 3000 + 5000 category SALARY, 1 EXPENSE amount 1500 category FOOD), 1 VOIDED, 1 PENDING.
- **(action)** GET /api/users/1/transaction-summary with valid Bearer token.
- **(expect)** 200 — userId=1, name="Ahmed Hassan", totalTransactions=5, completedTransactions=3, voidedTransactions=1, totalIncome=8000, totalExpenses=1500.
- **(verify)** No direct JDBC connection from user-postgres to transaction-postgres. The transaction aggregates come from a Feign HTTP call.

#### [S1-F4] Deactivate User Account

**Branch:** feat/M3/user/S1-F4/<studentID>  
**Endpoint:** PUT /api/users/{id}/deactivate

**M1 implementation:** Two cross-service writes on the shared database — SELECT COUNT(*) FROM budgets WHERE user_id = ? AND status = 'ACTIVE' plus UPDATE transactions SET status='VOIDED' WHERE user_id = ? AND status='PENDING'.

**M3 change:** Replace both with cross-service calls:

- **Active-budget pre-check** — Feign → budget-service GET /api/budgets/user/{userId}/active-count → returns int. If > 0, throw 400 ("User has active budgets"). The pre-check is best-effort: there is a TOCTOU race against a concurrent S4-F4 batch-create — between the count read and the deactivation save, a new ACTIVE budget could be created for this user. M3 accepts this race as an operator-resolution case (S1-F4 succeeds, the new budget remains for the deactivated user, and an operator can manually reconcile via S4-F7 purge or S4-F2 status update). Stricter consistency would require a distributed lock outside the M3 scope.

- **Pending-transaction void** — Replace the direct UPDATE on transactions with a user.deactivated event publish. transaction-service consumes the event and atomic-UPDATEs the user's PENDING transactions to VOIDED (per §16 Rule 11).

If the active-budget pre-check passes, set status = DEACTIVATED in user-postgres, save, then publish user.deactivated to the user.events exchange.

```java
@FeignClient(name = "budget-service", url = "${feign.budget-service.url}")
public interface BudgetServiceClient {
    @GetMapping("/api/budgets/user/{userId}/active-count")
    int getActiveBudgetCount(@PathVariable Long userId);
}
```

**Test scenario:**

- **(setup)** User ID=1 in user-postgres (status=ACTIVE). Budget in budget-postgres: userId=1, status=ACTIVE, category=FOOD. Transaction in transaction-postgres: userId=1, status=PENDING.
- **(action)** PUT /api/users/1/deactivate → Feign → budget-service returns active-count=1.
- **(expect)** 400 — "User has active budgets". User status unchanged. No event published.
- **(setup)** Update the budget status to COMPLETED in budget-postgres.
- **(action)** PUT /api/users/1/deactivate → Feign returns active-count=0.
- **(expect)** 200 — user status = DEACTIVATED in user-postgres. RabbitMQ user.deactivated event published with payload {userId: 1}.
- **(verify after event processing)** The PENDING transaction in transaction-postgres now has status=VOIDED.

#### [S1-F6] Top Savers by Net Income

**Branch:** feat/M3/user/S1-F6/<studentID>  
**Endpoint:** GET /api/users/reports/top-savers?startDate={date}&endDate={date}&limit={n}

**M1 implementation:** JOIN users ON transactions.user_id = users.id GROUP BY users.id ORDER BY (SUM(income) - SUM(expenses)) DESC on the shared database, taking the first limit rows.

**M3 change:** user-service cannot JOIN the transactions table (it lives in transaction-postgres). Instead:

1. Fetch all users from user-postgres.
2. For each user, call Feign → GET /api/transactions/user/{userId}/net-income?startDate=&endDate= on transaction-service → returns NetIncomeDTO {netSavings, transactionCount} (netSavings = totalIncome - totalExpenses over COMPLETED transactions in the date range).
3. Sort users by netSavings descending, take first limit.
4. Build and return List<TopSaverDTO> with fields {userId, name, netSavings, transactionCount}.

**Note on date filtering:** Pass startDate and endDate as query params to the transaction-service endpoint so it filters server-side rather than fetching all transactions, so that the interface would be:

```java
@FeignClient(name = "transaction-service", url = "${feign.transaction-service.url}")
public interface TransactionServiceClient {
    @GetMapping("/api/transactions/user/{userId}/net-income")
    NetIncomeDTO getUserNetIncome(
        @PathVariable Long userId,
        @RequestParam String startDate,
        @RequestParam String endDate
    );
}
```

**Test scenario:**

- **(setup)** 3 users in user-postgres: User A (Ahmed), User B (Sara), User C (Khaled). In transaction-postgres, all March 2026 COMPLETED transactions: User A net +3000 (5000 INCOME − 2000 EXPENSE), User B net +8000 (10000 INCOME − 2000 EXPENSE), User C net −500 (1500 INCOME − 2000 EXPENSE).
- **(action)** GET /api/users/reports/top-savers?startDate=2026-03-01&endDate=2026-03-31&limit=2.
- **(expect)** 200 — [{userId: B, name: "Sara", netSavings: 8000, transactionCount: …}, {userId: A, name: "Ahmed", netSavings: 3000, transactionCount: …}].
- **(verify)** user-service made Feign calls to transaction-service for each user's net income. No direct query on transactions table.
- **(action)** startDate=2026-04-01&endDate=2026-03-31 → 400.

#### [S1-F9] Find Users by Currency Preference with Minimum Transactions

**Branch:** feat/M3/user/S1-F9/<studentID>  
**Endpoint:** GET /api/users/preferences/currency?currency={c}&minTransactions={n}

**M1 implementation:** JSONB query on users table (preferences->>'defaultCurrency' = ?) + subquery counting COMPLETED transactions rows by user_id.

**M3 change:**

1. Query user-postgres for users whose preferences->>'defaultCurrency' matches the given value (local JSONB query — preferences lives on the users row).
2. For each matching user, call Feign → GET /api/transactions/user/{userId}/completed-count → returns long.

## Section 8 — Transaction Completion Saga & Cancellation Cascade

### 8.1 What Is a Choreography Saga

When a business transaction spans multiple services, there is no distributed rollback. The Choreography Saga achieves eventual consistency through:

- **Forward path:** each service listens for the previous step's success event and executes its part.
- **Compensation path:** on failure, the failing service publishes a failure event; every service that already committed reverses its local change on receipt of the compensation event.

**Theme adaptation (Finance Tracker):** the M3-STRUCTURE template names this section "Order Lifecycle Saga & Cancellation Cascade" because the canonical theme (Talabat) finishes with a customer-initiated payment. Finance Tracker has no payment service — S5 is the reporting-service. The saga still has the same choreography topology (one trigger event, fan-out to four consumers, a tail success/failure step that S3 listens for, a compensation cascade) but the tail step is "S5 generates a report-audit snapshot" rather than "user pays". There is also no separate customer-initiated step in the middle of the cascade — the entire flow is automatic from the moment S3-F4 fires transaction.completed. The cascade ends when S5 publishes report.completed (success terminus → status REPORTED) or report.failed (triggers compensation).

**Why S1's column shows no fan-out publish.** In the forward-cascade diagram above, S2 publishes account.stats-updated, S4 publishes budget.usage-updated, and S5 publishes report.initiated after consuming transaction.completed — but S1 publishes nothing. This asymmetry is deliberate: user-service maintains its transaction-stats counter locally (in users row columns) and no downstream service needs to react to user-stat changes. S2/S4/S5 emit fan-out events because their state changes feed reporting-service's audit-trail (report_audit_trail) and S5-F11 / S5-F10 dashboards. S1 has no analogous downstream consumer for user-stat events, so the spec deliberately omits a user.stats-updated publish to keep the event surface minimal.

### 8.3 S3-F4 — Complete Transaction (Saga Trigger)

**Branch:** feat/M3/transaction/S3-F4/<studentID>  
**Endpoint:** PUT /api/transactions/{id}/complete

**M1 implementation:** Set status = COMPLETED + completedAt. If balance was not already updated during approval, update the account's balance now. Update the matching budget's spentAmount for this category via a native SQL UPDATE on the shared budgets table (this is the cross-service write that M3 must remove).

**M3 change:** Remove the direct UPDATE budgets SQL. Run three Feign pre-checks, then publish transaction.completed and let budget-service consume it asynchronously.

**Behavior:**

1. Find transaction by ID → 404 if not found.
2. Validate status = APPROVED → 400 if not.
3. Pre-saga Feign checks (all three must pass before any event is published):
    - Feign → user-service GET /api/users/{userId} → status must be ACTIVE; if 404 or DEACTIVATED → 400
    - Feign → account-service GET /api/accounts/{accountId} → status must be ACTIVE; if 404 or FROZEN/CLOSED → 400
    - Feign → budget-service GET /api/budgets/user/{userId}/active?category={category} → 404 is acceptable (no budget for this category — the consumer will skip the update). Any other Feign failure → 400.
4. Mark transaction status = COMPLETING, set completedAt to now(), save.
5. Publish transaction.completed to transaction.events exchange with payload {transactionId, userId, accountId, category, type, amount, completedAt}.
6. Return 200 with the updated transaction.

Transaction transitions COMPLETING → REPORT_PENDING asynchronously when S3 consumes the report.initiated event from reporting-service. Final transition to REPORTED + COMPLETED happens when report.completed is consumed.

**Test scenario:**

- **(setup)** Transaction ID=1 in transaction-postgres: status=APPROVED, accountId=10, userId=1, category=FOOD, type=EXPENSE, amount=500. User ID=1 in user-postgres: status=ACTIVE. Account ID=10 in account-postgres: status=ACTIVE, balance=1500 (already debited at approval). ACTIVE Budget in budget-postgres: userId=1, category=FOOD, budgetAmount=2000, spentAmount=300.
- **(action)** PUT /api/transactions/1/complete.
- **(expect)** 200 — transaction status=COMPLETING. transaction.completed published to transaction.events.
- **(verify)** No direct UPDATE on budgets from transaction-service.
- **(verify after event processing)** budget-postgres budget spentAmount=800; reporting-postgres has a new PENDING SavedReport linked via JSONB reportConfig.transactionId=1; transaction-postgres transaction status=REPORT_PENDING (after report.initiated) → REPORTED (after report.completed).
- **(action)** Same transaction with user status=DEACTIVATED → Feign → user-service returns DEACTIVATED → 400. No event published.
- **(action)** Same transaction with account status=FROZEN → 400. No event published.
- **(action)** PUT /api/transactions/999/complete → 404 (transaction not found). No Feign pre-checks issued; no event published.

### 8.4 S3-F7 — Void Transaction (Compensation Trigger)

**Branch:** feat/M3/transaction/S3-F7/<studentID>  
**Endpoint:** PUT /api/transactions/{id}/void

**M1 implementation:** Two cross-service writes on the shared database — UPDATE accounts SET balance = balance ± ? WHERE id = ? (reverse the approval-time balance change; for TRANSFER, reverse on both source and destination) plus implicit "unbudgeting" if the transaction had been counted (though M1 spec only requires balance reversal explicitly).

**M3 change:** Remove the direct UPDATE accounts write. Publish transaction.voided — account-service consumes it and reverses the balance in its own database; budget-service consumes it and rolls back any spentAmount it may have applied; user-service and reporting-service apply their own reversals.

**Behavior:**

1. Find transaction by ID → 404 if not found.
2. Capture the current status into a local variable prev (used as previousStatus in the published event).
3. Validate prev IN (PENDING, APPROVED) → 400 if not. Saga-managed statuses (COMPLETING, REPORT_PENDING, REPORT_FAILED) cannot be voided directly via this endpoint — they are exclusive to the saga's automatic compensation path (§8.2 cascade), which is the sole publisher of transaction.voided for those statuses. Allowing direct voids of saga-managed transactions would race with the compensation cascade and produce duplicate transaction.voided events on the same transaction. Already-VOIDED, REPORTED, or REVERTED transactions also reject with 400.
4. Set transaction status = VOIDED.
5. Publish transaction.voided to transaction.events exchange with payload {transactionId, userId, accountId, toAccountId, category, type, amount, previousStatus: prev, reason: "user_requested"}.
6. Return 200.

Account balance reversal, budget rollback, and any saga-generated SavedReport archival happen asynchronously — the four downstream services each consume transaction.voided and update their own databases.

**Test scenario:**

- **(setup)** Transaction ID=1 in transaction-postgres: status=APPROVED, accountId=10, userId=1, type=EXPENSE, amount=500, category=FOOD. Account in account-postgres: balance=1500 (debited at approval). Budget in budget-postgres: spentAmount=300 (not yet incremented because txn was never COMPLETED).
- **(action)** PUT /api/transactions/1/void.
- **(expect)** 200 — transaction status=VOIDED. transaction.voided published with previousStatus: "APPROVED".
- **(verify after event processing)** account-postgres account 10 balance=2000 (S2 consumer detected previousStatus=APPROVED and reversed); budget-postgres budget unchanged (no completion increment to roll back).
- **(action)** Try voiding a fully-REPORTED transaction → 400 ("REPORTED is final-success; cannot be reversed via this endpoint").
- **(action)** Try voiding a transaction in saga-managed status (COMPLETING / REPORT_PENDING / REPORT_FAILED) → 400 ("saga-managed; reversal happens via compensation cascade, not direct void").
- **(action)** Try voiding a PENDING transaction (balance was never affected) → 200; transaction.voided published with previousStatus: "PENDING". S2 consumer sees previousStatus=PENDING and skips the balance reversal.
- **(action)** PUT /api/transactions/999/void → 404 (transaction not found). No event published.

### 9.3 JWT Global Filter

Bring the M2 JwtService (singleton from M2 §3.6) and the JWT-validation logic into the api-gateway as a GlobalFilter (Ordered = -1 so it runs before routing). The gateway filter must:

- Pass-through /api/auth/** (register and login do not yet have a JWT)
- Parse Authorization: Bearer <token> on all other routes; validate signature + expiry against the shared JWT_SECRET
- On success, forward X-User-Id, X-User-Role, X-Correlation-ID headers to the downstream service
- On failure, return 401 with no downstream call

**Required amendments for reactive integration** — Spring Cloud Gateway is reactive (Project Reactor / WebFlux), so the M2 servlet-stack JWT filter cannot be reused 1-to-1. The M2 filter was a servlet OncePerRequestFilter using HttpServletRequest / HttpServletResponse; rewrite it as a GlobalFilter that returns Mono<Void>. Concretely:

- Replace OncePerRequestFilter with implements GlobalFilter, Ordered (return -1 from getOrder() so it runs before routing).
- Replace HttpServletRequest / HttpServletResponse with ServerWebExchange (exchange.getRequest(), exchange.getResponse()).
- Wrap the blocking JWT validation in a non-blocking boundary: Mono.fromCallable(() -> jwtService.validateToken(token)).subscribeOn(Schedulers.boundedElastic()) so JJWT's blocking signature verification runs on a non-event-loop thread. Failing to do this will pin the Reactor event loop under load.
- Replace filterChain.doFilter(req, res) with return chain.filter(exchange); — and where the M2 filter executed code after doFilter returned, use the WebFlux chain.filter(exchange).then(...) continuation pattern.
- Forward parsed claims as headers via exchange.mutate().request(r -> r.header("X-User-Id", uid).header("X-User-Role", role).header("X-Correlation-ID", cid)).build() — the WebFlux ServerHttpRequest is immutable, so use the mutator pattern.
- Reject with 401 by setting exchange.getResponse().setStatusCode(HttpStatus.UNAUTHORIZED) then return exchange.getResponse().setComplete(); — do NOT throw exceptions for auth failures (reactive convention).

The JwtConfigurationManager Singleton from M2 stays as-is (not Spring-managed); only the filter shell is rewritten.

The shared JWT_SECRET is read from a K8s Secret mounted as an env var (see §10.5 Deployment example) — the gateway's JwtService reads it via @Value("${JWT_SECRET}") at startup.

The per-service M2 JWT filter remains as defense-in-depth: even if the gateway filter is bypassed (e.g., a dev-only port-forward to a service ClusterIP), the per-service filter still validates.


### MDC Population

- **correlationId** — populated by a servlet filter (`OncePerRequestFilter`) that reads the `X-Correlation-ID` header set by api-gateway and calls `MDC.put("correlationId", value)`. The filter must clear MDC in `finally`. RabbitMQ consumers must also read the `correlationId` header from the inbound `Message` and call `MDC.put` at the start of the listener method.

- **Entity IDs** (`userId`, `accountId`, `transactionId`, `budgetId`, `reportId`) — populated manually by service-layer methods using `MDC.put("transactionId", id.toString())` immediately before performing the operation, paired with `MDC.remove(...)` in a `finally` block to prevent leaking IDs into unrelated subsequent requests.

- **routingKey** — set by RabbitMQ publishers and consumers to the routing key being processed (e.g., `transaction.completed`, `report.failed`). This makes the Layer 3 RabbitMQ event audit panel (§11.3) usable.

### Required Log Points

Each service must emit logs at the following points so the LogQL panels in §11.3 have data to query. Use SLF4J: `private static final Logger log = LoggerFactory.getLogger(<Class>.class);`

| Log point | Level | Suggested message format |
|-----------|-------|--------------------------|
| Controller method entry | INFO | `"Received {} {}"` (HTTP method, path) |
| Controller method exit | INFO | `"Returning {} for {} {}"` (status, method, path) |
| Feign call — before request | INFO | `"Calling {}.{} with args={}"` (client, method, args) |
| Feign call — after success | INFO | `"{}.{} returned successfully"` (client, method) |
| Feign call — exception caught | WARN | `"Feign call to {} failed: {}"` (service, exception message) |

| RabbitMQ — event consumed (start) | INFO | `"Consuming {} for {}={}"` (routingKey, entityName, id) |
| RabbitMQ — event processed (success) | INFO | `"Processed {} for {}={}"` (routingKey, entityName, id) |
| RabbitMQ — consumer error | ERROR | `"Failed to process {}: {}"` (routingKey, exception message) → DLQ |

## 11.3 LogQL Panel Options (choose ≥ 3 per service)

A LogQL query is built up in three layers, and every panel below uses all three:

- **Label** — `{app="financetracker", service="transaction-service", level="ERROR"}` — match log streams by the labels emitted by the Loki4J appender (§11.1). This narrows down which streams the rest of the query reads from.
- **Line** — `|= "search-text"`, `!= "exclude"`, `| json`, `| line_format "{{...}}"` — filter and parse individual log lines within the matched streams. Because messages are JSON (§11.1), `| json` exposes every field (`correlationId`, `transactionId`, `routingKey`, …) for further filtering.
- **Aggregator** — `count_over_time(...[1m])`, `rate(...[5m])`, `sum by (service) (...)` — turn the matching lines into time-series numbers that Grafana can plot.

### Available Panels

**Error rate panel** — Count of ERROR-level log lines per service per minute.
- *Example purpose:* Spike detection — if transaction-service logs 50 ERRORs in one minute, something is wrong.

**Correlation ID trace panel** — Filter all log lines by a specific `X-Correlation-ID` value across all services.
- *Example purpose:* Trace a single transaction-completion request from api-gateway through transaction-service, budget-service, and reporting-service.

**RabbitMQ event audit panel** — Lines emitted by event publishers and consumers, filtered by routing key.
- *Example purpose:* Show how many `transaction.completed` events were published vs. how many `report.initiated` events were consumed in the last hour.

**Feign call outcomes panel** — Log lines for successful Feign responses vs. `FeignException` catches.
- *Example purpose:* Detect when account-service is degraded — transaction-service Feign calls to it start throwing exceptions.

**Saga state transitions panel** — Log lines at each saga step filtered by `transactionId`.
- *Example purpose:* Visualize the complete saga flow for transaction ID=42: `COMPLETING` → `REPORT_PENDING` → `REPORTED`.

**Slow operation warnings panel** — Log lines where elapsed time exceeded a threshold.
- *Example purpose:* Alert when S5-F10 financial health score aggregation takes > 5 seconds across its four Feign calls.

---

## 11.4 PromQL Panel Options (choose ≥ 3 per service)

A PromQL query is built up in four layers, and every panel below uses all four:

- **Metric** — the metric name itself, e.g., `http_server_requests_seconds_count` or `jvm_memory_used_bytes`. These are exposed by each service's `/actuator/prometheus` endpoint and scraped by Prometheus every 15s.
- **Label** — narrow the metric down with label matchers, e.g., `{service="transaction-service", uri="/api/transactions", method="GET"}`. Labels come from Spring Boot's Actuator metrics and from the `job_name` set in `prometheus.yml`.
- **Range** — append a time window in square brackets, e.g., `[5m]` or `[1h]`. This turns the instant counter into a sequence of samples over that window so the function in layer 4 has data to operate on.
- **Function** — `rate(...)`, `increase(...)`, `histogram_quantile(0.99, ...)`, `sum by (uri) (...)`, `topk(5, ...)` — converts the range vector into the final per-second rate, percentile, top-N, or grouped aggregate that Grafana plots.

### Available Panels

**HTTP request rate panel** — Requests per second per endpoint.
- *Example purpose:* Which transaction-service endpoints are under the most load during peak hours?

**HTTP latency percentiles panel** — P50/P95/P99 latency per endpoint.
- *Example purpose:* P99 latency on `GET /api/accounts/{id}/dashboard` is 4s — Feign enrichment is slow.

**JVM health panel** — Heap usage, GC pause duration, thread count.
- *Example purpose:* Memory pressure before OOM — reporting-service heap at 90% after running 10,000 health-score queries.

**Database connection pool panel** — HikariCP active connections vs. pool size.
- *Example purpose:* Pool exhaustion alert — budget-service using 10/10 connections during transaction-completion fan-out.

**Cache hit/miss ratio panel** — Redis cache hits vs. misses from `cache_gets_total`.
- *Example purpose:* S2-F12 dashboard cache hit rate — verify caching is effective.

**RabbitMQ throughput panel** — Messages published vs. consumed per queue.
- *Example purpose:* Consumer lag on `report.saga-listener` — published count > consumed count by > 100.

## 11.5 Observability Stack (K8s — monitoring namespace)

The three observability tools — Loki, Prometheus, and Grafana — run as their own pods inside the cluster, in a dedicated namespace called `monitoring`. Keeping them separate from the `financetracker` namespace means observability resources (CPU, memory, restarts) are isolated from the application services, and an issue in the app does not take down the dashboards.

The data flow uses two opposite directions:

- **Logs (push):** Each Spring Boot service runs the Loki4J appender (§11.1), which pushes log lines as JSON over HTTP to `http://loki.monitoring.svc.cluster.local:3100/loki/api/v1/push`. Loki itself never reaches into the services — they send to it.
- **Metrics (pull):** Prometheus scrapes each service's `/actuator/prometheus` endpoint on a 15-second interval (configured below). "Scrape" here just means an HTTP GET — Prometheus pulls the current metric values from each service and stores them as time-series.
- **Dashboards:** Grafana is configured with two datasources — Loki (for LogQL panels) and Prometheus (for PromQL panels). The 5 dashboard JSON files (one per service) are committed to the repo and provisioned into Grafana via a ConfigMap mount.

### Components

| Component | Image | Role in the stack |
|-----------|-------|-------------------|
| Loki | `grafana/loki:2.9.4` | Receives JSON log streams pushed by Loki4J from each service. |
| Prometheus | `prom/prometheus:v2.51.2` | Pulls metrics from each service's `/actuator/prometheus` every 15s. |
| Grafana | `grafana/grafana:10.4.2` | Dashboard UI; runs the LogQL/PromQL queries from §11.3 and §11.4. |

Cross-namespace DNS resolution makes this work: from `monitoring`, Prometheus reaches a service in `financetracker` using the fully qualified name `<service-name>.financetracker.svc.cluster.local`. From `financetracker`, services push logs to `loki.monitoring.svc.cluster.local`.

### Two Namespaces Required

The cluster must contain two namespaces, each defined as its own YAML file under `k8s/namespaces/`:

| Namespace | Purpose | YAML file |
|-----------|---------|-----------|
| financetracker | All 5 application services + their PostgreSQL + RabbitMQ + NoSQL stores. Already declared in §10.2. | `k8s/namespaces/namespace.yaml` |
| monitoring | Loki + Prometheus + Grafana only. Nothing application-related deploys here. | `k8s/namespaces/monitoring-namespace.yaml` |

## 12.1 How Services Reference Files From Other Modules

The `contracts/` module is the mechanism that lets all 5 services share Feign interfaces, DTOs, and event records without duplicating any Java code. It is a plain Maven JAR (no Spring Boot parent, no executable) that the 5 services depend on.

### Parent pom.xml — Module Aggregator

The root `pom.xml` lists every module in build order. Maven's reactor builds `contracts` first because the 5 services declare it as a `<dependency>`:

```xml
<modules>
    <module>contracts</module>
    <module>user-service</module>
    <module>account-service</module>
    <module>transaction-service</module>
    <module>budget-service</module>
    <module>reporting-service</module>
    <module>api-gateway</module>
</modules>
```

### contracts/pom.xml — The Shared Types Module

```xml
<project>
    <modelVersion>4.0.0</modelVersion>

    <parent>
        <groupId>com.<teamID>.financetracker</groupId>
        <artifactId>financetracker-m3</artifactId>
        <version>1.0.0</version>
    </parent>

    <artifactId>contracts</artifactId>
    <packaging>jar</packaging>

    <dependencies>
        <dependency>
            <groupId>org.springframework.cloud</groupId>
            <artifactId>spring-cloud-starter-openfeign</artifactId>
        </dependency>
    </dependencies>
</project>
```

The `spring-cloud-starter-openfeign` dependency is required because the `@FeignClient` annotation lives on interfaces inside this module. Event records and DTOs are plain Java records and need no extra dependencies.

### Each Service pom.xml — Depends on contracts

Add this to `user-service/pom.xml`, `account-service/pom.xml`, `transaction-service/pom.xml`, `budget-service/pom.xml`, and `reporting-service/pom.xml`:

```xml
<dependency>
    <groupId>com.<teamID>.financetracker</groupId>
    <artifactId>contracts</artifactId>
    <version>1.0.0</version>
</dependency>
```

The `api-gateway` does not depend on `contracts` (it does not call Feign clients itself; it just forwards HTTP requests).

### How Java Code Imports Across Modules

Once a service depends on `contracts`, every type defined there is importable like any other Java package. For example, `user-service` calling `transaction-service` via Feign:


### Build Order — Maven Reactor Handles It Automatically

Run `mvn clean install` from the repo root. Maven's reactor:

1. Detects that `user-service` (and the other 4 services) depend on `contracts:1.0.0`
2. Builds `contracts` first, installs it into the local Maven repo (`~/.m2/repository/com/<teamID>/financetracker/contracts/1.0.0/`)
3. Builds the 5 services in any order (no inter-service dependencies — they all only depend on `contracts`)
4. Builds `api-gateway` last (or in parallel with services)

For local Docker dev (`docker-compose up`), each service's Dockerfile copies its own JAR — the `contracts` JAR is already baked into the service JAR via Maven's shade/repackage plugin during step 3.

### Why This Eliminates Cross-Slice Compile Blockers

When student A starts work on S1-READ-DB (which calls `TransactionServiceClient.getUserTransactionSummary(...)`), they need that interface to exist in `contracts/` so their code compiles. Day-0 kickoff ensures:

- All 5 Feign client interfaces + all DTOs + all event records are committed to `contracts/` on Day 0, before any of the 15 slices begin work
- Student A's `user-service` compiles immediately because `TransactionServiceClient` exists in the imported `contracts` JAR — even though student G (owner of S3-READ-DB) hasn't yet implemented the matching endpoint
- Runtime testing: student A uses `@MockBean TransactionServiceClient` until student G's branch merges

## 13.2 The 15 Deliverables (Summary)

**Rule:** Each deliverable is a vertical slice that touches all parts of M3 — Java code, Kubernetes manifests, and observability artifacts. No deliverable is purely Java, K8s, or YAML. The 15 slices are designed so every team member works in parallel without blocking anyone else.

The 15 deliverables are organized as **5 services × 3 vertical slices per service**:

- **Slice A — Read & DB:** DB isolation, outbound Feign clients, exposed read endpoints, Postgres K8s, ≥3 LogQL panels, Logback config
- **Slice B — Events & Saga:** RabbitMQ topology, publishers/consumers, saga participation, Spring Boot K8s, ≥3 PromQL panels, actuator config
- **Slice C — Cross-Cutting Infra:** that service's gateway route entry + scrape job entry + dashboard JSON aggregation, plus one assigned shared-infra item

### Parallelism Strategy

The 15 slices are designed so nobody waits for anyone else. The key is **contract-first development**: every cross-service interface is agreed in a kickoff meeting on Day 1, written down, and committed before any feature work starts. From that moment, each member writes against the contract — not against another member's implementation — so they can compile, test (with mocks), and deploy their slice independently.

#### Day-0 Kickoff Contracts

Committed by the team lead (~2 hours):

- **Feign client interfaces** — every `@FeignClient` interface signature and the DTOs they return
- **Event payload records** — every record class (`TransactionCompletedEvent`, `ReportFailedEvent`, …)
- **New endpoint paths + DTO shapes** — exact path, query params, response JSON
- **K8s Service names** — `loki`, `prometheus`, `rabbitmq`, `<svc>-postgres`
- **Shared YAML stub files** — `api-gateway/application.yml`, `prometheus-configmap.yaml`, `grafana-dashboards.yaml`

#### Compile-Time Independence

Once the `contracts/` module is in place, slice 1's `TransactionServiceClient.getUserTransactionSummary(...)` call compiles even if slice 7 hasn't implemented the matching endpoint yet. The interface is the only thing needed to compile.

#### Runtime Independence (Mocking)

For local dev, each slice uses `@MockBean` on Feign clients and Testcontainers RabbitMQ. A slice can run, deploy, and verify in isolation.

#### Disjoint File Ownership

Each slice writes to its own packages and YAML blocks. Shared YAML files (`api-gateway/application.yml`, `prometheus.yml`, `grafana-dashboards.yaml`) have a stable structure so each slice edits only its assigned block. Merge conflicts are minimized.

#### Deploy-Time Independence

When a slice's branch is ready, it merges into `main` whenever. No slice blocks another.

# Section 16 — Critical Rules

1. **No cross-service JDBC.** After M3, no service opens a JDBC connection to another service's database. Zero tolerance.

2. **Feign for reads. RabbitMQ for side-effects.** Use Feign when you need data to continue processing. Use RabbitMQ when triggering a state change in another service.

3. **Auto ACK with DLQ routing.** Use Spring's default `acknowledge-mode: auto` with `default-requeue-rejected: false`. Spring ACKs when the listener returns normally and rejects when it throws.

4. **DLQ for every queue.** Every consumer queue has a dead-letter queue. Failed messages are never silently dropped.

5. **StatefulSet for all databases.** Never use plain Deployment for a stateful database.

6. **PostgreSQL 17.** Image pin is `postgres:17` in every StatefulSet. PG 18 breaks Hibernate native query implicit cast operator resolution.

7. **Explicit constructor injection.** No Lombok `@RequiredArgsConstructor`, `@Data`, `@Getter`, `@Setter`, `@Builder`.

8. **JWT validation at gateway.** Individual services retain their M2 JWT filter for defense-in-depth, but the gateway is the public-facing validator.

9. **No new tests added during grading.** The supplied test suite is the source of truth.

10. **15 deliverables, contract-first parallel work.** No slice waits for another slice's implementation; `contracts/` is the only Day-0 dependency.

11. **Atomic consumer mutations.** Every event consumer that mutates state must use a single atomic SQL UPDATE. Canonical pattern for `spentAmount`:
    ```sql
    UPDATE budgets SET spent_amount = spent_amount + :amount 
    WHERE user_id = :userId AND category = :category AND status = 'ACTIVE'
    ```

12. **Idempotent consumers.** Every event consumer must be idempotent. Two acceptable patterns:
    - **(a) State-conditional UPDATE:** Only succeeds once, e.g., `UPDATE saved_reports SET status='PENDING' WHERE transaction_id=:txnId AND status IS NULL`
    - **(b) Per-service processed_events table:** Check before applying; transactionally insert with the mutation

13. **Save + publish atomicity.** Cross-service event publishing after local DB write must be reliable. Two approaches:
    - **(a) Outbox pattern (recommended):** Save entity AND insert pending outbox row in same `@Transactional` scope; separate scheduled task drains outbox to RabbitMQ
    - **(b) At-most-once accept:** Publish after `@Transactional` commit; document that broker outage leaves PG with new state but no event
